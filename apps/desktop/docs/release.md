# Desktop release and verification boundary

`rin` desktop is a Tauri v2 application. The release surface is intentionally split
between a normal local build and a signed release build:

- `tauri.conf.json` contains the application identity and the `nsis`, `deb`,
  `appimage`, and `dmg` bundle targets. Its updater configuration has an
  empty public key and no endpoints so the plugin can initialize in ordinary
  builds without creating a usable update channel.
- `tauri.release.conf.json` is an explicit release overlay. It enables
  `bundle.createUpdaterArtifacts: true` and the GitHub Releases endpoint. The
  release job must create a temporary merged config with the real
  `TAURI_UPDATER_PUBLIC_KEY` before invoking Tauri; the updater plugin requires
  that public-key content in the final merged configuration.
- `tauri-plugin-updater` is registered in the Rust builder. A future frontend
  updater UI still needs the updater guest package and capability permissions;
  this shell currently keeps the updater registration Rust-side and does not
  claim that an update was installed.

## Sidecar contract

Tauri's `bundle.externalBin` entry is the logical name
`binaries/rin-sidecar`. For each target, the source file must be target-suffixed:

```
src-tauri/binaries/rin-sidecar-x86_64-unknown-linux-gnu
src-tauri/binaries/rin-sidecar-x86_64-pc-windows-msvc.exe
src-tauri/binaries/rin-sidecar-x86_64-apple-darwin
src-tauri/binaries/rin-sidecar-aarch64-apple-darwin
```

Run the existing builder with an explicit target:

```sh
pnpm exec node apps/desktop/scripts/build-sidecar.mjs \
  --target x86_64-unknown-linux-gnu
```

The Rust shell calls `app.shell().sidecar("rin-sidecar")`; the logical name is
intentional. Tauri resolves the target suffix while bundling and exposes the
packaged executable to the shell plugin. The sidecar builder runs both a
`--help` check and a Host runtime smoke that waits for `/api/status`. This
proves the staged runtime works on the native build host; the installed-bundle
E2E remains a separate boundary.

The target file is a native Node executable, not a `pkg` snapshot. Before the
Tauri bundle runs, the native runner stages `sidecar-runtime/entry.mjs`, the
compiled Host graph, web distribution, dependencies, and built-in repository
under `src-tauri/sidecar-runtime/`. It uses pnpm's hoisted deploy layout so
Tauri does not need to preserve pnpm module symlinks. The resources mapping
ships that tree; Rust resolves it from `app.path().resource_dir()` and passes
the entry module as the first sidecar argument. Native runner builds are
therefore required for each target platform; cross-compiling the Node runtime
is not supported.

## Signed updater release

Keep these values outside Git:

- Repository variable `TAURI_UPDATER_PUBLIC_KEY`: the public key generated by
  `tauri signer generate`. It is safe to publish, but must be the real key for
  the release lineage.
- Repository secret `TAURI_SIGNING_PRIVATE_KEY`: the matching private key,
  supplied as key content or a path understood by the Tauri CLI.
- Optional `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the key password.

The private key must never be copied into a config file, workflow artifact, or an
installer. Losing or rotating it without a migration plan prevents existing
installations from accepting future updates. The repository intentionally does
not generate a key during CI and does not use a placeholder key as if it were
valid.

A signed release should produce:

- Linux: AppImage plus its `.sig` (the Debian package remains the normal
  installer).
- Windows: NSIS setup executable plus its `.sig`.
- macOS: the `.app.tar.gz` updater bundle plus its `.sig` (the DMG remains the
  normal installer).
- A `latest.json` whose URLs and signatures point at the same published
  release assets.

An installer uploaded as an ordinary workflow artifact is not an update
release. The release must publish both the artifact and signature, and an
installed previous version must check the HTTPS endpoint before this path is
called operational.

## Clean-machine E2E

`.github/workflows/desktop-e2e.yml` builds the Linux web frontend and
target-suffixed sidecar, builds a Debian installer, installs it on a fresh
Ubuntu runner, and launches `/usr/bin/rin` with a sanitized `PATH` and no
Node environment variables. It waits for `/api/status` with `status: "ok"` on
port 8320, force-kills the GUI, and checks that the sidecar parent watchdog
removes the orphaned Host process.

This is a Linux installation/start smoke test. It does not prove Windows NSIS
installation, macOS DMG installation, OS code signing/notarization, or a
published updater. Those require their own runners and credentials.
